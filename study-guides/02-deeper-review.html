Separate three kinds of confidence

Measured / executedReference comparisons, 30 training steps, 1/2/4 ranks, fresh-environment reproduction on this Mac.
Derived from codeLoss normalization, expert ownership, permutation inverse, theoretical payload and parameter storage formulas.
Not establishedLinux execution, GPU performance, production robustness, model quality, general arbitrary batch sizes.

Correct output alone does not establish correct training. Correct training on fixtures does not establish good scaling. A storage formula does not measure peak device memory.

Why inspect the loss before the distributed wrapper?

The intended global objective determines gradient normalization. Communication can deliver the correct tensors with the wrong scale. Derive the mathematical gradient first, then inspect whether the collectives implement that derivation.

Concrete review findings worth knowing

These are observations from reading the current code. Proposed tests below are review exercises, not additional tests already run. The guides do not change the submitted implementation.

1. How to independently validate an exchange

Review exercise · communication.Exchange
Weak objectiveF(x) = ½‖Px‖²
For any permutation P, F(x) = ½‖x‖².
ConsequenceA squared-norm check cannot detect row misordering.

For a development check, give each source row a unique tag and each destination position a distinct weight. Compare received rows with an independently constructed source-to-destination map, then compare backward gradients with the inverse map. The submitted correctness suite instead tests the complete model against a full-model reference.

2. Empty destination ≠ empty source

Boundary gap · ParallelMoEBlock.forward()

The code preserves a graph path for m=0 received rows, but the learned-routing suite does not force that case. It also does not test n=0 input tokens on a source. reshape(len(x), 2, -1) cannot infer the final dimension from zero elements when len(x)=0.

Proposed check: a separate development fixture could route all tokens to one owner and check the zero-receive ranks. For empty sources, either extend and test the implementation or retain the current N≥world_size input contract.

3. Read per-step errors, not just the maximum

Reporting improvement · verify.py

`verify.py` compares first-step outputs, gradients, and parameter updates across independently launched standard and parallel jobs; it compares loss every epoch and final parameters. The saved comparison summary reports each error category. Every parallel replica is compared with the standard model.

4. Averaging can hide short-lived hot experts

Measurement improvement · show_results.py

The reported imbalance is max(mean per-expert assignments) / mean assignments. This can conceal alternating hot experts across steps. The new per-step routing logs permit inspection of transient hot experts; proposed summary additions include per-step maximum/mean, peak assignments per owner, and distributions across steps. Owner load matters because an owner may hold multiple experts.

5. Portability and robustness have a boundary

Validation gap

Only ARM64 macOS was executed. The existing CPU/Gloo design is intended to be portable, but that is not a Linux result. A fresh Linux environment should run the same pinned install and complete suite. Fault injection, cancellation, and multi-host behavior are also not validated by a collective timeout alone.

Why not claim “deleting received * 0 must deadlock”?

The current code also calls every local expert on empty tensors, which can preserve graph dependencies. Removing just one safeguard may leave another path intact. To test graph disconnection, explicitly define the changed empty branch and inspect the resulting graph. Predict the whole graph, not a single line in isolation.

Make every scaling claim earn its wording

Supported storage claimShared storage: 10,560 bytes/rank.
Expert storage: 268,288 / W bytes/rank.
Total: 278,848 → 77,632 bytes/rank from W=1 to W=4.
Unsupported shortcut“Memory drops 4×” conflates expert storage with total parameters, gradients, optimizer states, activation peaks, and process memory.

Each expert has (32×64+64)+(64×32+32)=4,192 parameters. Eight float64 experts occupy 268,288 bytes. Block projection plus router have 1,320 parameters, or 10,560 bytes. Derive those counts before quoting the table.

The one-rank baseline uses MoEModel with local blocks and no token exchange, while multi-rank jobs use the same model class with parallel blocks. Compare end-to-end behavior while stating this execution-path difference. Learned routing can evolve across steps; compare workload metrics alongside timing.

How would you discuss GPU scaling without inventing a speedup?

Explain the competing terms: sharded expert compute and storage versus dispatch/return bandwidth, latency, load imbalance, and replicated shared work. Then propose a GPU experiment with synchronized device timing, representative batch/expert sizes, grouped GEMMs, and communication profiling. State that CPU measurements do not determine the crossover point.
